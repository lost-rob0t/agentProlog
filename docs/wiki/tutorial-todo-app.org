* Goal and limits

You will start with an empty application workspace, configure an explicitly trusted coding agent, ask it to create a dependency-free Node.js todo app, review individual native approvals, and run an independent HTTP checker.

The target is one generated file, =app.mjs=. It serves an HTML interface and real create/read/update/delete endpoints. Todos live in an in-memory collection: restarting the application loses them. This tutorial does not implement restart persistence, browser automation, deployment or a production security boundary.

The instructions describe the implementation in the documentation checkout based on =0512eb8=, not a promise that an older or unmerged =main= has these features. The sources linked below are the executable authority. All live-provider commands are optional instructions for an authorized operator; writing this tutorial did not execute paid model calls.

* 1. Prepare an isolated workspace

Complete [[file:installation.org][Installation]]. You need the AgentProlog checkout, Nix, an existing authorized OpenRouter credential if you choose the live path, and a Node executable supporting the stable =--permission= flag used by the independent checker. The packaged app uses Node.js 22; for source commands, enter =nix develop= and check the actual Node on =PATH=.

In a shell at the AgentProlog checkout:

#+begin_src sh
export AGENTPROLOG_TUTORIAL_REPO="$PWD"
export AGENTPROLOG_TUTORIAL_ROOT="$HOME/agentprolog-todo-tutorial"
export AGENTPROLOG_TUTORIAL_WORKSPACE="$AGENTPROLOG_TUTORIAL_ROOT/workspace"
export AGENTPROLOG_TUTORIAL_NODE="$(node -p 'process.execPath')"
test ! -e "$AGENTPROLOG_TUTORIAL_ROOT"
#+end_src

If the last command fails, stop and choose a different unused root; do not overwrite a previous app or its evidence. If it succeeds, create the directories:

#+begin_src sh
install -d -m 700 "$AGENTPROLOG_TUTORIAL_ROOT"
mkdir -p "$AGENTPROLOG_TUTORIAL_WORKSPACE/.agentprolog"
install -d -m 700 "$AGENTPROLOG_TUTORIAL_ROOT/state"
"$AGENTPROLOG_TUTORIAL_NODE" --permission -e 'console.log("Node permission flag available")'
#+end_src

The project path is the =workspace= subdirectory. State and the operator file live outside that workspace. Keep the exported variables in this shell for configuration loading and restart. None of these variables contains a credential.

Only the last command above executes Node, and its inline program is fixed by you, not generated by a model. If the permission flag is unsupported, use a compatible Node build before proceeding; do not remove the checker's restrictions to get a green result.

* 2. Write the acceptance contract first

Create =$AGENTPROLOG_TUTORIAL_WORKSPACE/requirements.txt= in your editor, with the following content:

#+begin_example
Build a dependency-free Node.js HTTP CRUD todo app in one file app.mjs.
Export createServer() returning a node:http Server.
Importing the module must not listen automatically.
When run as node app.mjs, listen on process.env.PORT or 3000 on 127.0.0.1.

GET / serves a usable HTML todo interface with input, list, add, edit,
complete and delete controls. The browser uses fetch against these endpoints:

GET /api/todos -> 200 JSON array, initially [].
POST /api/todos {title:string} -> 201 {id,title,completed:false}.
IDs must be unique. Reject blank/nonstring titles with 400.
PATCH /api/todos/:id {title?:string,completed?:boolean} -> 200 updated todo.
Validate values with 400, and return 404 for an unknown ID.
DELETE /api/todos/:id -> 204 empty body; unknown ID -> 404.

Edits/deletes affect later GET responses and preserve other todos.
Use JSON error responses and an in-memory collection.
No external dependencies, network services, secrets or shell commands.
Do not create any other file. The app will be started and HTTP-tested
independently. Do not claim browser interactions were automated.
#+end_example

This is an application contract, not a request for a code snippet in chat. The existing acceptance script uses the same core target. Do not relax the contract after a failed run simply to declare success.

** Project: tools and provider

Create =$AGENTPROLOG_TUTORIAL_WORKSPACE/.agentprolog/config.pl= with:

#+begin_src prolog
:- module(todo_tutorial_project, [agentprolog_config/1]).
:- use_module(library(agentprolog_workspace_tools), [workspace_tools/2]).
:- use_module(library(agentprolog_check_tool), [syntax_check_tool/3]).
:- use_module(library(rlm_chain), []).

agentprolog_config(_{
    profile:todo_tutorial,
    mode:direct,
    tools:Tools,
    capabilities:[
        tool(workspace_read),
        tool(workspace_create),
        tool(workspace_write),
        tool(workspace_check),
        context(peek)
    ],
    runtime_options:[
        provider(Provider),
        provider_name(openrouter),
        prompt_compile_mode(all_tools),
        planner_max_tokens(6000)
    ],
    budget:_{
        max_model_calls:16,
        max_iterations:24,
        max_total_tokens:65536,
        max_output_bytes:131072,
        max_cost_usd:0.04
    }
}) :-
    getenv('AGENTPROLOG_TUTORIAL_WORKSPACE', Root),
    getenv('AGENTPROLOG_TUTORIAL_NODE', Node),
    workspace_tools(Root, FileTools),
    syntax_check_tool(Root, Node, Check),
    append(FileTools, [Check], Tools),
    rlm_chain:openrouter_provider('openai/gpt-4.1-mini', Provider).
#+end_src

The installed host exposes these AgentProlog modules on its Prolog library path. =Root= and =Node= must be the absolute paths exported in step 1. A wrong/missing variable is a configuration error, not an instruction to guess a path.

The provider constructor uses the runtime's environment credential reference for =OPENROUTER_API_KEY=. The value must come from your existing authorized credential mechanism, not the Prolog file, prompt, repository or generated app. No fallback provider is configured. To use another route, deliberately change the constructor/name and validate it using [[file:providers-and-budgets.org][Providers and budgets]].

*Security:* these Prolog modules and the coding package are trusted executable code. Tool capability limits do not sandbox their loading directives or predicates. Read the files before authorizing them. The confined workspace tools defend their own paths and content preconditions; they are not an OS sandbox against hostile concurrent processes.

** What each tool actually does

| Tool | Arguments of interest | Effect and limit |
|------+-----------------------+------------------|
| =workspace_read= | =path= | Reads a bounded UTF-8 file and returns its content, byte count and SHA-256 |
| =workspace_create= | =path=, =content= | Creates a new file; never overwrites an existing one; native write approval |
| =workspace_write= | =path=, =content=, =expected_sha256= | Replaces an existing file only if the current hash still matches; native write approval |
| =workspace_check= | =path= | Fixed =Node --check=; native process approval, not execution of the app |

Paths are relative to the configured workspace. Absolute paths, =..= traversal and symlink chains are rejected; the file tools require existing parent directories and cap file content at 65,536 bytes. =workspace_tools/2= also registers =workspace_modify=, but this tutorial does not grant its capability: use the explicit hash-guarded =workspace_write= repair path.

=workspace_check= takes no arbitrary command or argument list, uses no shell, clears the subprocess environment and bounds diagnostics and execution time. Its output includes =path=, =sha256=, =exit_code= and =output=. The handler has a five-second execution bound. An exit code of zero proves JavaScript syntax for that content, not HTTP behavior.

Native tool results are opaque context. The model must inspect the returned alias with =context_peek=; the result is not necessarily included inline in its tool message. The selected builder instructions say this explicitly. Use =context_peek= with selector type =item= and index =0= when inspecting the referenced result item, as in the actual acceptance objective.

* 5. Ask for actual implementation

The CLI accepts each submitted line as an objective. Paste this as one line at =agentprolog>=:

#+begin_example
Read requirements.txt with workspace_read and inspect its opaque result with context_peek. Build the complete app by creating app.mjs with workspace_create; do not merely suggest code. Use only the supplied workspace tools and create no other file. Read app.mjs back to confirm it exists. Run workspace_check on app.mjs, inspect its result context, and repair syntax errors with workspace_write using the current SHA-256. Do not claim the HTTP or browser tests passed: an independent host will run the HTTP checker. Inspect opaque result aliases with context_peek, selector type item, index 0, as needed.
#+end_example

The agent should read the requirements, propose the new file through a real tool, read it back and request the fixed syntax check. If it only prints code, ask for the actual confined-tool operation; do not count that answer as an implementation.

* 6. Review every offered approval

Look in the Approvals and Tools sections. For each pending operation, inspect:

- The actual tool/effect and exact approval ID.
- The relative target =app.mjs= and its resolved workspace confinement.
- The proposed content for creation/replacement and the precondition hash for an edit.
- The distinction between a write and the =process= effect for =workspace_check=.

Only if the individual request matches the task, copy its real ID and offered choice:

#+begin_example
/approve ACTUAL_PENDING_ID allow_once
#+end_example

Replace =ACTUAL_PENDING_ID= with the ID currently displayed. To refuse an unexpected operation, use that approval's offered =deny= choice; =/cancel= can stop the current run. Never infer “approve all future requests” from this tutorial.

Expect a separate native approval for the syntax checker even though it does not execute the app: it still launches a bounded process. A tool capability grant is not an effect approval. Pending native execution resumes through the runtime after a valid decision; stale decisions after restart are not reusable approvals.

When the turn ends, =/inspect= should show successful native mutation/read observations and a =workspace_check= observation with =exit_code: 0=. Read the diagnostics if the exit code is nonzero. A tool invocation can successfully report a syntax failure; inspect the returned exit code rather than treating the existence of an observation as a pass.

If =app.mjs= already exists, do not approve another create operation. Have the agent read it, inspect the current =sha256= and use =workspace_write= with that =expected_sha256=. A stale hash means the file changed; reread and review rather than bypassing the check. Repairs are additional work and may incur more provider usage. Decide their budget explicitly; the manual path does not provide the acceptance script's cumulative repair accounting.

* 7. Verify independently, without another model call

Exit the agent with =/quit= before executing the generated application. Review =app.mjs= as code, not just the model's summary. The repository's independent checker imports the exported factory, listens on an ephemeral loopback port and makes actual HTTP requests.

From the checkout, run this adapter for an arbitrary manually generated workspace:

#+begin_src sh
cd "$AGENTPROLOG_TUTORIAL_REPO"
env -u OPENROUTER_API_KEY -u ZAI_API_KEY \
  "$AGENTPROLOG_TUTORIAL_NODE" --input-type=module - \
  "$AGENTPROLOG_TUTORIAL_WORKSPACE" <<'JS'
import { verifyTodoApp } from './packages/conversation-ui/test/todo-app-proof.js';
const checks = await verifyTodoApp(process.argv[2]);
console.log(JSON.stringify({status: 'passed', checks}, null, 2));
JS
#+end_src

This invokes the actual [[file:../../packages/conversation-ui/test/todo-app-proof.js][verifyTodoApp]] helper, not a made-up command-line mode. It makes no model/provider request. The syntax-check child has an empty environment; the server child receives only the fixed =PATH=/=HOME=/=NODE_ENV= environment set by the checker, not provider credentials. Its Node filesystem permission flags limit reads/writes to the workspace, subprocess permission is not granted, and the heap is bounded. These are not OS sandboxing or network isolation; review generated code and use stronger isolation if needed.

The checker validates:

- A successful HTML response containing an input, script and API reference.
- An initially empty JSON list.
- Creation of two todos with distinct IDs.
- Listing, updating title/completion, and observing the updated state.
- Selected invalid-input cases and missing-ID responses.
- Deleting one todo while preserving the other.

The returned check keys are =html=, =create=, =list=, =update=, =delete=, =validation= and =isolation=. The HTML checks establish markup presence, not working browser click behavior. The checker is also not an exhaustive validator for every possible malformed request in the written contract. It starts a fresh server; it does not test restart persistence or guarantee graceful import behavior for every incorrect implementation.

If it fails, preserve the diagnostics. A repair objective should reproduce the original requirements, state the actual independent failure and request =workspace_write= against the current source hash. Rerun the same checker after repair. Never replace the HTTP checks with “the model says it works.”

To test the checker itself, without a model call:

#+begin_src sh
node --test packages/conversation-ui/test/todo-app-proof.test.js
#+end_src

The positive fixture is a functional server; the negative fixtures are a static mock and an unstartable module. These are test controls, not model-produced artifacts or evidence of a live provider run.

* What counts as completion

Keep these claims separate:

| Observation | What it establishes |
|-------------+---------------------|
| Model prints plausible code | A suggestion, not a file mutation |
| Native mutation succeeds | A real file changed under the recorded approval/preconditions |
| =workspace_check= returns zero | That content passed Node syntax checking |
| Canonical run outcome is complete | The runtime finished that run, not external app acceptance |
| Independent HTTP checker passes | Its concrete HTTP/markup assertions passed for the tested source |
| Manual browser checks succeed | An operator exercised those UI interactions |
| Recorded receipt passes | The recorded route/native evidence binds to the current source and fresh HTTP checks |

None of these establishes durable todo storage, browser automation, production readiness or permission to publish/deploy the app.
