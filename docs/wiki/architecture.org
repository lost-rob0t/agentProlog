* One product, one runtime

AgentProlog is an application composed over Prolog-RLM, not a competing agent runtime. The dependency direction is =AgentProlog -> Prolog-RLM=. The flake consumes the upstream default package; it does not vendor a runtime implementation. The current executable is a Node terminal client paired with a SWI-Prolog session host, not the Bubble Tea frontend described in early planning documents.

* Configuration is trusted code; skills are data

An explicitly supplied operator module exports =agentprolog_options/1=. Product/plugin/project modules export =agentprolog_config/1=. Local packages are ordinary SWI packs with =pack.pl= and =prolog/agentprolog_plugin.pl=; there is no second package manager or dependency resolver. A project-local =.agentprolog/config.pl= requires explicit trust and is rejected, not silently ignored, when present without that trust.

These modules are consulted executable Prolog, with arbitrary host-process authority. Capability checks constrain runtime requests, not malicious initialization directives in trusted modules. Use a fresh sidecar process for each project. Never derive executable configuration paths/options or closures from model output.

By contrast, native skill documents contain exactly one =agentprolog_skills([...]).= data term. The loader reads terms without consulting directives, bounds documents/bodies, validates upstream prompt units and adds source/hash provenance. A skill cannot grant capabilities, expand budgets or declare itself mandatory/always active. Selection still passes through the upstream compiler.

Configured instructions or native skills currently use a non-streaming host callback that forwards through the canonical upstream provider wrapper. This is a projection limitation, not an alternative compiler or provider engine. See [[file:../../test/agentprolog_skills_test.pl][skill projection tests]] and [[file:api-reference.org][callback reference]].

* Canonical execution lifecycle

1. The packaged CLI resolves the project and state directory, then spawns the bundled session host without a shell. Alternatively, an operator selects an external canonical sidecar.
2. The host loads trusted configuration, acquires the state directory's non-waiting =owner.lock=, opens the upstream effect store and creates/restores its checkpoint.
3. The client negotiates =prolog_agent_ui_v1= and required capabilities. A successful negotiation alone is insufficient: =Client.connect()= waits for a validated canonical snapshot before accepting commands.
4. A =session.turn= command admits its request ID durably before asynchronous dispatch. It starts a fresh run/view for the supplied objective. A blank objective requests a question; =question.answer= starts execution with that answer.
5. The host creates a native tool registry and invokes =rlm_direct_execute/4= in =direct= mode or =rlm_completion/4= in =rlm= mode. Both are upstream runtime paths, not independent local agent loops.
6. Native callbacks produce canonical semantic events through the upstream UI facade/reducer. Tool observations, text, usage, traces, questions and approvals are projected by the JS client; the UI does not execute tools or choose model actions.
7. In =direct= mode, a suspended native approval retains execution state. An exact =allow_once= decision resolves upstream authority and resumes the cursor; denial rejects execution. Cancellation releases pending work/cursor. Restart marks in-flight/suspended work interrupted instead of replaying it. Typed-plan approvals in =rlm= mode are not wired into this product continuation bridge.
8. A terminal stream is not itself task success. Inspect =view.state.run.outcome.status=. Accepted artifacts retain =published:false=; there is no generic product publication command.

The host supports one configured durable session per state directory. =session.create= and =session.select= return/refresh that session; they are not multi-session workspace discovery APIs. =session.resume= explicitly starts a new run for the previous objective; it is not crash-transparent resumption of a native cursor. Ordinary follow-up turns are fresh objective runs, not a promise of automatically preserved multi-turn model history.

* Persistence and recovery

| State file | Role |
|------------+------|
| =owner.lock= | One host owns the state directory; concurrent owners fail rather than sharing execution |
| =session.json= | Versioned product checkpoint: IDs, canonical view, phase, objective, configuration binding and request receipts |
| =effects.db= | Upstream durable effect store opened for this session |
| =session.json.tmp= | Temporary checkpoint used before atomic rename |

The configuration binding includes normalized configuration and hashes of recorded source files, including operator config, pack manifests and selected skill sources. A different configuration/project binding is rejected. This does not claim a complete transitive dependency hash or an OS sandbox.

Admitted requests are retained with command/payload identity. An exact duplicate receives its stored receipt; reuse with a different payload is a conflict. An interrupted admitted request carries =recovery:"inspect_snapshot_before_retry"=. Receipts are bounded to 1024; this is not indefinite exactly-once operation storage. The JS client does not automatically retry uncertain commands and normally generates a fresh request ID for each call.

Disconnect leaves the last view visibly stale. Reconnect closes the old process, starts the operator-configured sidecar and replaces the projection with its canonical checkpoint. Duplicate/old events are ignored; sequence gaps or session mismatches fail closed. Runtime persistence, not rendered terminal output, is authoritative.

* Current boundaries, not roadmap promises

- Prolog-RLM has a broader public API than AgentProlog exposes. The local configuration loader allow-lists runtime options; the canonical host allow-lists commands. An upstream predicate's existence does not make it a wire operation or CLI feature.
- The JS projection understands subagent events. The bundled host does not advertise a subagent capability, offer a =/spawn= command, or implement a product subagent scheduler. Named agents are selectable configurations, not evidence of an implemented autonomous multi-agent team UI.
- =mode:rlm= invokes upstream completion. This does not expose every upstream workflow, Spec/Plan/Verify operation, expert API or evolution API as a product feature.
- DeepSeek Harness uses a distinct version-1 operation bridge, not the canonical conversation client's protocol. Its current package is a service/lifecycle slice; full AgentFactory/workspace UI and evolutionary-product integration are not established by those transport tests.
- Zara support is an optional profile of the existing Prolog-RLM runtime, not a second runtime identity or a dependency from Zara to AgentProlog.
- Deterministic/native fixture success, recorded real-provider artifacts and fresh live acceptance are different evidence. No current hosted or live pass is inferred from checked-in scripts or old status prose.
